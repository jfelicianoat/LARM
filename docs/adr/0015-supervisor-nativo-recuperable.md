# ADR-0015 — Supervisor nativo recuperable de procesos

Estado: aceptado para los componentes internos P021/P093; integración pública y H07 completo pendientes. Fecha: 2026-11-01. Contrato público 3.13.0 intacto.

El host conserva actualmente el Job Object y el drenaje de IO del worker en memoria. Tras morir el host, un PID, un archivo de ancla o un flag persistido no acreditan el cierre de todos sus descendientes y canales. Además, asignar un Job Object después de crear el proceso deja un intervalo previo a esa asignación.

Se incorpora un modo privado del binario, `worker-guardian`, que se ejecuta como proceso dedicado. Antes de ejecutar código del adaptador se asigna a su propio Job Object exterior, con kill-on-close y sin breakaway. Los descendientes heredan esa pertenencia al crearse; el Job Object interior del Worker sigue vigente. No se añade código `unsafe` ni se amplían las excepciones existentes.

El supervisor retiene el Worker, sus supervisores reales de salida/stdout/stderr y el Job Object exterior. La pérdida del stdin del propietario solicita cierre. La terminación del árbol usa los handles de identidad y pertenencia nativa revalidada del host; excluye únicamente al supervisor. `CLOSED` exige IO realmente drenado y una consulta al objeto nativo que confirme que solo queda el supervisor. Cada consulta vuelve a comprobarlo. El supervisor permanece vivo tras ese cierre hasta recibir `RELEASE`; desactiva kill-on-close solo después de volver a observar que está solo y termina sin ejecutar más adaptadores.

La recuperación usa un named pipe local con la DACL existente del SID del operador y SYSTEM, rechazo de clientes remotos y una instancia de servidor retenida entre clientes. El descriptor persistible contiene versión interna, sesión, fence y clave pública; no contiene PID autoritativo, nombre de pipe arbitrario, secretos ni flag de cierre. Cada respuesta firma con Ed25519 un reto nuevo, su acción, descriptor completo, estado e identidades diagnósticas. Un estado antiguo firmado no responde a un reto nuevo. La semilla privada y el entorno viajan únicamente por el stdin heredado; no van a argumentos, logs ni archivos. La lectura inicial y los mensajes están acotados.

Si el supervisor desaparece, el Job Object inicia la terminación de sus hijos, pero la ausencia del pipe o del proceso continúa siendo un error de observación: no autoriza liberar recursos. Esto favorece conservar recursos frente a declarar un cierre no demostrado. La política tras pérdida del supervisor o reinicio del sistema sigue pendiente.

Este componente bajo nivel no concede P022, no implementa `TransformationAttemptGuard`, no muta SQLite y no habilita la API de transformaciones. Su integración exige enlazar la cualificación y las rutas con la autoridad persistida antes de ejecutar, incorporar transporte de RPC, recuperar el journal del intento y probar H07 completo con el daemon público. Las pruebas actuales ejecutan el helper real y matan su propietario de prueba, no el servidor API de producción.

Referencias: [Job Objects de Microsoft](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) y [creación seguida de asignación a un Job Object](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812). La herencia del objeto exterior evita depender de que la asignación interior suceda antes de que el adaptador cree hijos.

## Integración del cliente cualificado (2026-11-01)

El descriptor interno 2 añade la identidad de instalación/run/perfil. El bootstrap distingue el caso básico del caso de transformación; este último solo lleva ruta de base e identidad del actor, y resuelve código, raíces y aprobación desde SQLite de solo lectura, sin crear ni migrar una base. Se compara la identidad esperada antes del handshake. Se reutilizan la cualificación física y las cuatro operaciones tipadas del host. El recibo sigue ligado al ejecutable del host: no se remide ni se vuelve a sellar para admitir un binario distinto.

Cada RPC exige además una firma de control con la clave privada que recibió el propietario por stdin. Un descriptor público permite observar/cerrar para recuperación, pero no reconstruir la ejecución. Acción, parámetros, acceso declarado, identidad y nonce participan en esa firma, con dominio distinto al de las respuestas. La respuesta firma también el resultado o error. Los mensajes quedan acotados a 512 KiB y los plazos de RPC son finitos. Las conexiones se atienden concurrentemente con un máximo de dieciséis, para que una llamada pendiente no bloquee observación/cierre. Un contador diagnóstico de llamadas activas nunca concede autoridad de cierre.

Después de validar la firma, cada RPC consume atómicamente su nonce UUIDv4. Se conservan hasta 4096 nonces en memoria durante toda la vida de ese helper, sin desalojo: al agotar la capacidad se rechazan nuevos RPC, manteniendo disponibles observación/cierre/retirada. Una firma inválida no consume el nonce; la repetición de un paquete válido no vuelve a invocar el backend. La autoridad de ejecución de una sesión no debe reutilizarse para otra instancia: la futura composición del journal debe generar y vincular una sesión/clave nueva por lanzamiento admitido.

El helper comprueba recibo/journal y perfil actuales desde SQLite antes y después de cada operación, además de las comprobaciones físicas y de acceso del cliente tipado existente. Ante pérdida de cualificación se conserva el primer error de operación y sigue disponible la limpieza. El helper no publica salidas ni escribe el catálogo o los jobs de Core.

`CLOSED` requiere también cero RPC activos. El vencimiento del observador no abandona el backend ni sus verificaciones físicas: la operación del Worker conserva su timeout existente y la llamada sigue contada hasta terminar las comprobaciones. Así no se acepta cierre mientras una comprobación aún puede conservar pins o lanzar un sondeo de identidad del sistema. La retirada solo aborta conexiones cuando esas operaciones ya han terminado.

Continúan pendientes el binding servidor previo a ejecución con el journal del intento, `TransformationAttemptGuard`, el transporte de progreso/cancelación por id, el productor/consumidor público y H07 integral con un job Core. La integración de RPC cualificado es un componente necesario y no acredita por sí sola esas fases.

## Registro del propietario nativo (incremento posterior, 2026-11-01)

El descriptor interno 3 incorpora metadatos de sesión/clave pública, revisión QUEUED, fence y binding de instalación/run/perfil/plan privado. El repositorio propone un claim sin escribir ni conceder ejecución. El helper valida esa propuesta contra SQLite y retiene los archivos originales tras comprobar SHA/tamaño/EOF antes del handshake. Puede preparar P022, pero rechaza transformación hasta encontrar su registro exacto confirmado. El claim vuelve a comparar revisión y propuesta, comprueba disponibilidad nativa antes y dentro de la transacción y confirma RUNNING, propietario, journal versión2 y evento/outbox juntos. Una lectura de postcondiciones detecta escrituras omitidas.

`NativeTransformationAttempt` combina el descriptor con respuestas vivas firmadas. El journal y el job deben conservar el mismo propietario; un guard antiguo o sin ese propietario no puede cerrar el intento. El helper registrado solo admite Execute del plan privado fijado, una única vez por lanzamiento, y Verify del job privado que devolvió. Ready no es una orden de transformación; Recheck conserva las comprobaciones físicas y de registro. Un único estado atómico coordina admisión, stop y retirada: no se confirma Release si entra una comprobación que todavía conserva recursos.

La conexión concurrente espera una instancia disponible únicamente ante `PIPE_BUSY`, antes de enviar bytes y dentro del plazo ya fijado por el observador/RPC. No reenvía operaciones tras un error de escritura o lectura ni convierte ausencia/error/plazo en prueba de cierre.

La recuperación de arranque conserva el propietario y la causa de interrupción sin liberar sus reservas. Otro proceso puede reconstruir el observador desde esos metadatos, pero solo una prueba viva de cierre de árbol/IO/calls permite el cierre transaccional y su replay. La pérdida del helper continúa fallando cerrado.

La aceptación de este incremento usa un controlador de prueba explícito para catálogo, mapeo de preview y lanzamiento del helper; mata/reinicia el daemon API real con un job Core y una llamada privada en vuelo. No acredita interrupción durante bytes parciales de conversión, consumidor público automático, recuperación de un lanzamiento no registrado, progreso/cancelación por id ni reinicio confirmado hasta publicación con conversores reales. Esas integraciones siguen pendientes; no habilita el motor público.

## Intención durable y reconciliación del daemon (2026-11-02)

Antes del handshake se registra `transformation.owner` con sesión/clave pública, fence/binding y contexto Core; nunca la semilla ni el bootstrap. Una propuesta de preparación proyecta la revisión QUEUED siguiente, sin escribir. La preparación confirma esa revisión CAS, el journal de intención PREPARING y su evento/outbox juntos. El helper exige esa intención exacta antes de abrir el input o ejecutar herramienta. La ruta antigua de claim no puede tomar un trabajo con preparación pendiente.

La transición a RUNNING confirma también REGISTERED en la intención. Cerrar o completar el intento confirma CLOSED en la misma transacción que el job y sus recursos. Se preserva la reconciliación de propietarios ya registrados con journal versión2 anteriores a esta intención; la ausencia del registro nuevo nunca concede permiso para liberar recursos. Los eventos verifican su fila y enlace de outbox después de insertar: un trigger AFTER no puede dejar una confirmación parcial aunque el contador de escrituras sea positivo.

`GuardianProcess` conserva el stdin heredado con un Child propio y ventana oculta. Perder al propietario cierra ese canal y solicita cierre al helper; no mata ni retira el testigo por observar un PID/exit code. El único bootstrap secreto se escribe en memoria y el pipe. La espera de salida sucede después de la retirada explícita y no se usa como prueba de cierre.

El arranque del daemon primero marca las ejecuciones interrumpidas y luego reconcilia sus propietarios en segundo plano, con páginas/concurrencia acotadas. Cada elemento valida el contexto y estado actuales antes de actuar, se conecta mediante retos firmados, solicita stop y exige árbol/IO/calls cerrados antes de confirmar la liberación. Solo después retira el testigo. Una preparación que perdió su propietario antes de RUNNING se adopta exclusivamente con ese cierre nativo comprobado y se termina como fallida recuperable, sin ejecutar. Ausencia, error o plazo de observación conservan recursos y se registran; no impiden servir la API ni recuperar otros elementos independientes. El esquema no resuelve todavía la pérdida definitiva del supervisor o el reinicio del sistema.

El actor de la petición/trabajo se conserva separado del actor de la cualificación y aprobación del backend, ya delimitado por la admisión de planes. El helper deriva este último del perfil persistido y vuelve a validar actor/hash/run/permiso; no lo toma de parámetros de herramienta ni del cliente. La lectura del trabajo sigue limitada a su propietario o administrador.

Las pruebas de este incremento cubren recuperación automática de un propietario registrado y de un helper todavía PREPARING, competencia, omisión/corrupción de escrituras y separación de actores. El servidor realiza la reconexión/cierre/liberación; el catálogo/mapeo de planes y admisión de prueba siguen explícitos. El productor/consumidor de transformación público, progreso/cancelación, salida observada hacia publicación y H07 completo continúan pendientes. La API de transformación conserva su rechazo por motor no disponible hasta integrar ese recorrido.

La recuperación retiene duplicados de los handles nativos de las mismas anclas del host/base y conserva esa propiedad en cada tarea. No readquiere la carpeta ni usa el epoch como autoridad. La parada avisa cooperativamente, deja terminar las transacciones en curso y espera al supervisor; una salida temprana solicita stop y el trabajo pendiente conserva su lease nativa hasta terminar. Esto evita liberar la exclusividad del anfitrión mientras una tarea todavía puede modificar su base.

La retirada del testigo es housekeeping posterior al cierre durable, separada de la liberación de recursos. El arranque recorre también propietarios ya CLOSED, incluidos los archivados en historial y registros anteriores sin intención lateral. Valida el vínculo con un intento realmente cerrado; si encuentra un helper vivo, solicita stop y exige otra respuesta nativa de cierre antes de retirarlo. Si no encuentra helper, no modifica recursos ni usa esa ausencia como prueba. No cambia job, intento, error o eventos al completar esta retirada. Se conserva el registro histórico para poder repetir la limpieza tras perder una respuesta de Release o caer entre el commit y la retirada.

## Salida observada del supervisor hacia publicación (2026-11-02)

El cliente privado del supervisor puede obtener `TransformationOutputManifest` opaco para un claim registrado. Valida antes de enviar el RPC el descriptor versión3 y la coincidencia de fence, binding sellado, trabajo/intento/instalación, propietario nativo y contexto Core. Exige respuestas nuevas de Recheck antes y después de Verify; el helper comprueba por su cuenta la cualificación y registro actuales y solo permite verificar el job privado devuelto por su único Execute. Un preview sin propietario registrado, un descriptor público o un manifiesto deserializado por el consumidor no pueden producir ese objeto opaco.

Este objeto acredita una respuesta observada, no integridad física ni cierre. El verificador existente sigue exigiendo cierre nativo vivo, volumen reciente, rutas/cotas y SHA/tamaño/EOF de archivos retenidos. La publicación conserva su ticket SQL previo a escrituras, CAS/manifiesto y finalización transaccional; el testigo se retira después del commit. Los hooks de runtime ausentes permanecen `NotRegistered` y no se inventan capacidades o límites.

La prueba nativa añade un cuarto intento al mismo trabajo: nuevo plan/admisión explícitos del controlador, conversión de referencia, salida observada por el helper, rechazo de etiquetas ajenas y de captura con writer vivo, corrupción física controlada rechazada y publicación completa. Esto conecta componentes de ejecución, verificación y publicación con el supervisor real. Continúan pendientes el productor/consumidor público y H07 por API con caída durante conversión y reinicio confirmado; este incremento no los sustituye.
