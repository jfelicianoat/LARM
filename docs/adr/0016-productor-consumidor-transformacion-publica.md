# ADR-0016 — Productor y consumidor público de transformación

Estado: implementación para validación, 2026-11-06. Contrato público 3.13.0 sin cambios. Este incremento no concede aceptación integral P093/H07 ni transforma los estados BLOCKED_REAL de sus dependencias.

El daemon compone el entorno físico, las políticas actuales y el motor de transformación detrás de las rutas públicas existentes. Solo se registra la receta de referencia Base64 que el host ya cualifica. La instalación lógica debe resolver a una única instalación actual, con run y perfil exactos; una receta, versión de herramienta o formato sin soporte se rechaza. No se deduce compatibilidad de otros conversores.

El preview cualificado permanece en el host y se cierra antes de responder. Core mapea el tamaño algorítmico de los datos y las cuotas impuestas de control/procedencia en fases por volumen observado. Las cuotas no medidas conservan confianza UNKNOWN con cota superior. UNKNOWN sin cota requiere presupuesto explícito; el presupuesto cubre el pico de asignación y el margen se exige por separado. La revisión del destino y el digest del perfil se incluyen en el paso Core sellado, usando el objeto request ya previsto por el contrato. No hay cambios de schema público.

Crear un plan no crea trabajo, reservas ni locks. Confirmar vuelve a observar input, destino, espacio y política, y confirma atómicamente admisión y una entrada privada transformation.dispatch. Esta entrada contiene contexto y vínculo de plan/intento; es una señal durable, nunca autoridad para ejecutar o liberar recursos. Solo se seleccionan trabajos QUEUED actuales sin propietario pendiente. El repositorio vuelve a comprobar el plan, cualificación, versiones y guards antes de preparar/reclamar el intento. Las entradas históricas no se consumen como nuevos permisos.

La repetición exacta se resuelve antes de tocar archivos o cualificación, mediante la misma identidad, cuerpo y revisión originales. Un reinicio conserva el trabajo y su historial, exige un plan nuevo confirmado y control de revisión, y crea otra señal durable en la misma transacción. Un hash, actor o revisión ajenos no producen recursos.

El consumidor espera a que termine el inventario de recuperación inicial antes de crear nuevas intenciones PREPARING. Conserva las mismas anclas nativas del host/base y serializa las operaciones de la receta de referencia, cuyo workspace privado es compartido. Las tareas de planificación/admisión conservan su propiedad aunque desaparezca la conexión HTTP. La parada solicita cierre y espera a esas tareas.

El lanzamiento sigue el protocolo ya aceptado: intención durable, bootstrap por stdin, Ready firmado, claim exacto, Execute y Verify ligados al intento. La salida observada debe superar cierre nativo vivo, medición física, validación y publicación CAS con ticket previo; solo después del commit se retira el testigo. Un resultado COMPLETED no se reescribe por un fallo posterior de housekeeping. No se acepta ausencia de proceso/pipe ni un flag SQL como prueba de cierre.

Las pruebas de aceptación de este incremento deben usar el productor HTTP y consumidor de producción, una cualificación P026 real y actores distintos, sin mapeo/admisión Core desde el controlador. El catálogo inicial y la contención del ledger privado son fixtures declarados. El controlador mata/reinicia su servidor propio, observa recuperación y solicita un reinicio público hasta publicación. Esta interrupción no demuestra caída durante bytes parciales de conversión. Siguen pendientes progreso/cancelación por id, pérdida definitiva del testigo/reinicio del sistema, conversores reales y aceptación de runtimes/UI. Una intención sin testigo observable conserva recursos y requiere la política todavía pendiente.
