# P099 — Perfiles externos por versión y fixtures de APIs reales

**BLOCKED_REAL, revalidado el 2026-10-22.** El recibo formal vigente registra 23 PASS, cero FAIL y dos procedimientos reales BLOCKED. La revalidación repitió probes de Ollama 0.40.6 para versión, API y generación de `gemma4:12b`, además de persistencia de locks/cualificaciones, binding de instalación, daemon, transporte Tauri, UI, formato y Clippy. Ninguna observación creó ni cualificó un lock. Implementé la adquisición determinista y una primera persistencia SQLite para locks inmutables de runtime. El flujo registra una captura local de fuente con revisión fijada y SHA-256 comprobado; el lock usa RFC 8785, la tupla runtime/fuente/revisión/versión/OS/build/backend/protocolo y exige exactamente los 22 campos del catálogo `runtime-profiles.json`. Tanto la herramienta como el repositorio permiten repetir una escritura idéntica y rechazan reemplazar un lock existente con contenido distinto.

El incremento actual publica `PUT /api/v1/runtime-profile-locks/{lock_sha256}` y `GET` sobre la misma ruta, conectados al mismo repositorio SQLite que consulta la admisión `runtime.install`. El `PUT` exige que la ruta coincida con el hash canónico, valida el DTO cerrado y registra como actor al principal autenticado; `GET` devuelve el lock sólo por hash exacto. Ambos conservan `UNQUALIFIED`; la API no puede promoverlo. El contrato de operaciones, el schema OpenAPI y el manual operativo incluyen estas rutas. Los tests HTTP cubren escritura/replay, lectura, scope, hashes y rechazo de promoción.

La pantalla de runtimes permite pegar un documento JSON para adquirirlo, consultar un lock por SHA-256 y revisar runtime, versión, sistema, build, backend y protocolo. La vista muestra siempre `UNQUALIFIED` y advierte que el registro no acredita compatibilidad ni permite instalar. El transporte Tauri acepta `PUT` dentro de la API loopback y conserva el token fuera del WebView.

Todos los locks que crea la herramienta quedan `UNQUALIFIED`, incluso si el documento tiene todos los campos y hashes válidos. El verificador rechaza manipulación del contenido y no admite cambiar el estado a `QUALIFIED`. Una versión `UNKNOWN` queda registrada como candidata no cualificada; el mecanismo no anuncia soporte, no crea perfiles habilitados y no ejecuta pruebas contra adaptadores.

La migración `0004_runtime_profile_locks` añade identidad única, almacenamiento del documento, restricciones `UNQUALIFIED` y triggers que prohíben editar o borrar. El repositorio emite journal, evento y outbox en una transacción; una repetición exacta no duplica esos registros. Sus seis tests SQLite cubren replay, conflicto de identidad, bloqueo de promoción/edición/borrado, hash y payload corruptos, actor inválido y rollback ante fallo de outbox. La admisión P031 de `runtime.install` ahora resuelve el hash persistido y comprueba `runtime_family`, versión upstream exacta y estrategia anunciada; los nueve tests de instalación cubren además lock ausente, familia/versiones desajustadas, estrategia no declarada y ausencia de escrituras al rechazar. El lock continúa `UNQUALIFIED`, así que esto no habilita ejecución. También pasan los ocho tests Python de adquisición: cubren los 20 candidatos y campos, hash y serialización deterministas, revisión y bytes de fuente, campos ausentes/extra, estrategias no declaradas, versión desconocida, manipulación del estado/hash, creación inmutable, replay y recorrido CLI acquire/verify.

Verificación del incremento anterior: el recibo P099 registró 16 pruebas PASS, ningún FAIL y 2 procedimientos REAL BLOCKED. Pasaron los tests HTTP P099, regeneración y comprobación de schemas, validación explícita del índice generado de capacidades, nueve tests SQLite de locks/cualificaciones, 13 tests de instalación, ocho tests Python de adquisición, compilación del daemon, cuatro tests del transporte Tauri, formato/Clippy de Tauri, las 52 pruebas de interfaz, build, lint, formato y Clippy del workspace. ### Incidencia de cierre del worker y revalidación (2026-10-21)

La primera ejecución de la suite completa dejó pruebas de cierre esperando. Se identificó que `taskkill /T /F` puede fallar con el usuario actual de Windows y que el propietario Tokio de `Child` no recibía una orden directa de terminación. El worker ahora envía la señal al task que posee `Child`, que usa `start_kill()` y espera la salida; la sonda raw del host aplica el mismo patrón. El intento de terminar el árbol queda como mejor esfuerzo. Esto conserva el cierre ordenado y la admisión hasta que finalicen proceso e IO; no sustituye el aislamiento ni el kill-on-close de Job Object pendientes de P130.

La prueba P023 `arranque_entorno_health_y_parada_reales` quedó en `health_unreachable` bajo el sandbox por el loopback local. Con red local habilitada pasó en 2.38 s. Después, `cargo test --workspace` pasó completo, incluidos `probe_raw_que_ignora_eof_se_termina_drena_y_reinicia_en_el_mismo_contexto`, los dos casos de cierre que antes excedían 60 s, todos los escenarios declarativos y los tests SQLite.
