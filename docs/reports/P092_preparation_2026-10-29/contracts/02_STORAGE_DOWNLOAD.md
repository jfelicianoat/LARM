# Almacenamiento, adquisición y recuperación

La unidad de reservas es volume_key: Volume GUID Windows; UNC=(servidor+share canonical casefold) con identidad verificable; si no puede comprobarse, UNKNOWN y bloquear auto-placement. Letra es atributo de presentación. Resolver ruta desde GUID+relative_path, GetFinalPathNameByHandle; validar que cada ancestro real queda bajo root permitido. Reparse points, symlinks, junctions, ADS y escapes se bloquean antes y después de abrir. FAT limita 4GiB por fichero; no autoelegir para artefacto mayor. Estados ONLINE, OFFLINE, READ_ONLY, LOW_SPACE, DEGRADED, UNKNOWN.

Preflight produce StorageEstimate del schema. Separar bytes en disco ya existentes de nuevas asignaciones. peak_extra(v)=máximo de bytes NUEVOS vivos simultáneamente por fase en volumen v; CAS existente no suma nueva asignación. Ejemplo fuente30+temp18+salida9 en mismo volumen: si fuente ya existe, total57 y extra27; si se descarga nueva, extra57. Copia a otro volumen mantiene source y reserva target íntegro. Descompresión suma fichero comprimido y contenido extraído mientras coexistan. required_free=peak_extra+max(1GiB, ceil(peak_extra*500/10000)); usable_free=OS_free-policy_minimum_free-reservations_otros. No descontar own_reservation dos veces ni volver a restar bytes ya consumidos de una reserva: reservation.remaining=reserved-created_live; OS_free ya refleja created_live. policy minimum es máximo por volumen entre roots, no suma. Admisión en BEGIN IMMEDIATE con snapshot libre <5s, comprobación checked y reserva por volumen; revalidar antes de cada fase y cada chunk.

EXACT=manifest tamaños y hashes por fichero; HIGH=Content-Length o LFS size pinned revision; ESTIMATED=intervalo con upper_bound evidenciado; UNKNOWN=sin límite superior. Admitir estimated sólo reservando upper bound; UNKNOWN bloquea job hasta refresh o presupuesto duro explícito en bytes del operador, que limita escritura y se audita. Confirmación sin presupuesto no habilita descarga. Destinos válidos: ONLINE/escribible/soporta tamaño/cumple reserva. BEST_FIT ordena priority desc, performance clase apropiada, menor espacio sobrante tras operación, id asc. Mostrar todas las alternativas y causas; selección manual usa iguales gates.

CAS layout root/blobs/sha256/ab/hash; temporal root/staging/job_id/artifact_id.partial; manifests root/manifests/variant_id.json con checksums y provenance para reconstrucción sin DB. Blobs inmutables, no modificar hardlinks; nunca mover un blob compartido sin actualizar referencias. Importar EXTERNAL es read-only y registra hash/tamaño; copiar crea propiedad nueva LARM_MANAGED. SHARED se borra sólo con refcount cero, leases cero, journal cero y dry-run aprobado con digest del plan.

Mover/delete/transform/todo writer toma locks ordenados volume_key, variant_id, artifact_id lexicográficos. Lease admission comparte guard artifact-use; move adquiere exclusive y rechaza ACTIVE_LEASE 409. Mantener journal durable fases PLANNED, LOCKED, COPYING, VERIFIED, DB_SWITCHED, ACCESS_TESTED, SOURCE_DELETED, COMPLETED. Copiar, fsync+hash, DB switch compare-and-swap row_version, abrir nuevo destino, sólo después borrar origen gestionado. Fallo antes de DB switch conserva origen y limpia destino provisional; después de switch, conservar ambos y reconciliar acceso antes de borrar. EXTERNAL nunca borrar; shared preserva referencias no trasladadas. Fallo/cancelación/reinicio en cada fase tiene oracle explícito. No usar rename crossvolume como transacción.

Descargas: pin revision y archivo, una stream por artifact, concurrency defaults. HTTP Range con ETag strong/If-Range o Last-Modified+hash pinned; 206 debe Content-Range coincidir. 200 al reanudar reinicia temporal tras nueva reserva; 416 sólo éxito si tamaño/hash final coincide. Content-Encoding identity. Persistir offset durable tras fsync chunk; checksum final obligatorio cuando upstream lo ofrece, de otro modo SHA256 local con trust DECLARED, no VERIFIED upstream. Retry sólo timeout/408/429/5xx; Retry-After acotado60s, cinco reintentos [1, 2, 4, 8, 16] con jitter reproducible job_id. 401 refresca una vez; 403gated solicita licencia; 404revision terminal. Cancelación limpia sólo temporales propios, libera reservas y conserva provenance.

Multi-fuente: mismo hash+size permite mirrors; prioridad autenticada disponible, revision fija, EXACT>HIGH>ESTIMATED, HTTPS, prioridad fuente desc, source_id asc. Sin hash común no mezclar segmentos de fuentes. Fallover empieza fichero de cero o conserva offset sólo con misma strong ETag y SHA. Local/UNC usa idéntico preflight/hashes. Git LFS valida OID sha256 y tamaño, no importa pointer como modelo. Se soportan GGUF shards, SafeTensors index, ONNX external_data, Diffusers directories, Transformers tokenizer/config, CT2 y MLC bundles, NCNN param/bin y MNN bundles mediante detectores de adapters.

Rebuild: escanear manifests+blobs, validar hashes, reconstruir relaciones en DB temporal, informe de conflictos, backup y sustitución sólo tras íntegra verificación. No inventar upstream/licencia de un blob huérfano. Limpieza inicial dry-run; LOW_SPACE pausa nuevas asignaciones, no borra modelos ni unload con lease.

Auto-placement admite ASK_ALWAYS (default, no autoelige), PREFERRED_LOCATION (id configurado; si no elegible ASK), MOST_FREE_SPACE (usable_free desc), FASTEST_STORAGE (NVME>SSD>HDD>NETWORK>REMOVABLE>UNKNOWN), BY_MODEL_TYPE (map configurable LLM/DIFFUSION/AUDIO, default sin asignar), CUSTOM_RULES (DSL de contrato03). Cualquier empate usa priority desc y id asc, tras los mismos hard gates. BEST_FIT es una política adicional explícita, nunca sustituto de estas seis. Performance class usa NVME, SSD, HDD, NETWORK, REMOVABLE, UNKNOWN; prueba de velocidad opcional y consentida en fichero temporal gestionado, no benchmark sobre datos del usuario.

resource_lock admite múltiples filas SHARED por recurso: clave(resource_id,operation_owner_id,generation), donde operation_owner_id es job_id/lease_id, distinto del principal autenticado. Acquisition en BEGIN IMMEDIATE comprueba que no hay EXCLUSIVE ajeno para SHARED ni ninguna fila ajena para EXCLUSIVE; inserta todos los recursos en orden global o revierte todo. Liberar sólo filas de ese owner/generation. Reconciliación de crash consulta journal/lease real antes de retirar un lock, nunca timeout arbitrario que permita writers simultáneos.

Las representaciones y reglas de los requisitos corregidos están completadas en [contrato 11](11_CONFORMIDAD_V3.md); aplicarlas junto con este contrato.

## Revisión 3.1.0 — planes de descarga P052

`POST /api/v1/download-plans` recibe `DownloadPlanRequest`. `optional_artifact_ids` puede omitirse (equivale a `[]`); si se envía, contiene IDs UUIDv7 únicos de artefactos opcionales del bundle verificado. Los artefactos requeridos siempre se incluyen. Un ID requerido, inexistente, duplicado o perteneciente a otro bundle se rechaza antes de planificar. `storage_location_id:null` solicita preflight de todos los destinos; un ID concreto solicita el plan para ese destino y conserva en la respuesta las alternativas elegibles y las razones de rechazo.

`ArtifactSizeEstimate` se conserva por archivo. EXACT lleva bytes y límites inferior/superior iguales, con evidencia de manifiesto fijado. HIGH conserva el valor y una cota superior respaldados por Content-Length, Git LFS u otra metadata de revisión fijada. ESTIMATED admite un valor estimado con cota superior o un intervalo con ambos límites y sin valor puntual. UNKNOWN lleva bytes y límites null, source UNKNOWN y motivo no vacío. Los bytes son strings decimales comprobados; cero es un tamaño conocido. El origen y `evidence_refs` acompañan cada tamaño conocido. No convertir un intervalo ni UNKNOWN en un tamaño puntual.

`DownloadPlanRequest.optional_artifact_ids` puede omitirse y equivale a `[]`. El mismo schema cerrado se usa en `source.download_plan`; el SDK fuente conserva ese campo cuando está presente y valida IDs UUIDv7 únicos. Una fuente que no pueda vincular los IDs del catálogo central con su manifiesto fijado devuelve `UNSUPPORTED_CAPABILITY` antes de preparar un plan; nunca ignora una selección no vacía. Los límites por archivo viajan en `ArtifactManifest.artifacts[].size_estimate`, que referencia `ArtifactSizeEstimate`; no se añaden campos de tamaño al request.

La respuesta `DownloadPlanResponse` devuelve cada artefacto del manifiesto con `required`, `selected` y su estimación, además de todas las alternativas de destino con su `StorageEstimate` y motivo. Con destino null, `plan_id`, `plan_hash` y `storage_estimate` son null: la respuesta sirve para elegir destino y no es ejecutable. Con un destino elegible, la respuesta contiene un plan inmutable cuyo hash liga variante/revisión, selección, archivos y hashes, tamaños y evidencias, origen, prioridad, presupuesto, destino y vencimiento. Crear un plan no crea job, no reserva espacio y no empieza transferencia.

`POST /api/v1/downloads` solo acepta `ExecuteDownloadPlan` con `operator_confirmed:true`, `plan_id` y el `plan_hash` exacto visto por el operador. La interfaz solicita esa confirmación explícita después de mostrar artefactos, certeza de tamaño y destino. El servidor vuelve a validar revisión, hashes, destino y reserva; en una transacción durable consume la confirmación, crea job/reserva/journal/outbox y registra actor y hora. Rechaza plan sin destino, caducado o cambiado, falta de confirmación y replay. El plan no autoriza ejecución por sí mismo.

La migración `migrations/0006_p052_artifact_size_estimate.sql` añade la estimación persistida. Las filas existentes reciben UNKNOWN con motivo de migración; el valor histórico de `expected_size` no se eleva a EXACT ni ESTIMATED sin evidencia.

## Revisión 3.10.1 — fuente principal y mirrors alternativos P052

`DownloadPlanResponse.source_candidates` contiene de 0 a 16 mirrors alternativos ordenados y cualificados; una lista vacía significa que no hay alternativas exactas y no bloquea el preflight ni la descarga desde la fuente principal. Cada mirror fija `source_id`, `variant_id`, `revision_id`, `revision_key`, hash del manifiesto, prioridad de fuente, confianza de tamaño, transporte HTTPS, estado de autenticación y el mapeo de cada artefacto seleccionado: ID del artefacto objetivo, ID en la variante fuente, ruta relativa, SHA-256 y tamaño exacto. No incluye URLs, tokens, credenciales ni valores secretos. `DownloadPlanResponse.source_id` identifica siempre la fuente principal de la variante elegida; ésta puede servir tamaños EXACT, ESTIMATED o UNKNOWN y no necesita aparecer en la lista de mirrors.

Sólo se admite un mirror con fuente habilitada, binding vigente, capacidades `download_plan` y `download_chunk`, cualificación P026 actual y permisos de red; toda cuenta, credencial o licencia exigida debe estar resuelta y autorizada antes de incluirlo. Un mirror debe fijar su revisión y cubrir exactamente todos los artefactos seleccionados con rutas normalizadas, SHA-256 y tamaño exacto iguales al plan objetivo. Los IDs de artefacto pueden diferir entre variantes y se ligan por ruta, hash y tamaño, nunca por nombre de modelo o canonical_model_id solos. Sin hash y tamaño exactos compartidos no hay mirror.

`DownloadPlanRequest.source_id`, cuando se envía, debe coincidir con la fuente principal de la distribución seleccionada; no selecciona un mirror ni cambia la procedencia del job. El servidor ordena las alternativas por autenticación disponible, confianza EXACT>HIGH>ESTIMATED>UNKNOWN, HTTPS, prioridad de fuente descendente y `source_id` ascendente. El plan hash cubre la fuente principal, la lista ordenada de mirrors y sus mapeos; incluso la lista vacía se serializa y se sella en planes nuevos. La activación revalida cada mirror fijado y falla como plan caducado si cualquiera cambió, se deshabilitó, perdió autorización o cualificación.

La ejecución prueba primero la fuente principal y usa mirrors alternativos por artefacto. Sólo permite fallback ante timeout, error de I/O, HTTP 408, 429 o 5xx; al cambiar de fuente elimina el staging parcial y comienza ese fichero desde offset cero. No mezcla bloques ni reintenta con otra fuente ante errores de autenticación, licencia, permisos, protocolo, revisión o integridad. Cada fallback confirmado persiste `download.mirror.failed` y su outbox junto al progreso durable, con job, artefacto, source IDs y reason code, sin URLs ni secretos. La procedencia final de cada artefacto registra la fuente y `revision_key` que realmente lo entregó; SQLite valida que ambas pertenezcan al plan sellado. Los registros anteriores sin `source_candidates` siguen usando sólo su fuente original, sin inferir mirrors; la verificación del hash antiguo se permite únicamente para esos planes vacíos.

## Revisión 3.3.0 — flujo de bloques source P051

Los adaptadores source pueden anunciar el método opcional `source.download_chunk` (contrato de adaptadores 1.1). Cada lectura liga source_id, job_id, plan_id/hash, approval_id nullable, revisión fijada, relative_path normalizada, offset, máximo por bloque y validador. El máximo es 512 KiB; la respuesta usa base64 para permanecer bajo el frame NDJSON de 1 MiB. No se transmite una URL de descarga ni una credencial al Core. La respuesta declara offset exacto, bytes, EOF, total nullable y validador nullable; el SDK rechaza offset distinto, bloque excesivo, base64 no canónico, overflow o contradicción entre EOF y total. En EOF el total pasa a ser exacto por observación.

El executor persiste el primer validador con el offset durable. Reanudar requiere el mismo ETag fuerte o Last-Modified ligado a SHA-256 fijado; si el adaptador informa un validador distinto o no puede validar la reanudación, el Core elimina el temporal propio y solicita desde offset cero. Siempre se verifica el SHA-256 completo tras EOF; sin hash upstream el resultado queda DECLARED. Cada bloque sigue sujeto a los gates del adaptador, permisos de red/lectura, cuenta y licencia, presupuesto y reservas del P051. Adaptadores existentes siguen siendo válidos sin esta firma, pero no cualifican para ejecución local de descargas.

## Revisión 3.12.0 — primera adquisición

La regla anterior de bundle verificado se limita a planes físicos heredados. Planes remotos nuevos seleccionan desde snapshot cualificado, sellan AcquisitionPlanBinding y revalidan antes de ejecutar. Sin confirmación no crean job/reserva; UNKNOWN exige presupuesto duro. Reglas completas: [revisión 3.12.0](REVISION_3_12_0_P044_P052.md).

## Revisión 3.12.1 — binding del plan source

La firma source.download_plan recibe SourceDownloadPlanRequest con acquisition opcional; referencia pública, hash upstream y mapa de IDs centrales permiten seleccionar una revisión sin consultar IDs privados. Selección y copia exacta source_acquisition_v1 quedan selladas. La petición HTTP del usuario se conserva. [Reglas y oráculos](REVISION_3_12_1_SOURCE_ACQUISITION.md).
