# Revisión de contrato LARM 3.11.1 — resolución de versiones P032/P100

Fecha: 2026-10-25. Predecesora: 3.11.0. Ámbito: aclaración de la selección efectiva de versión para leases, sin cambios en los schemas wire ni en la migración 0013.

## Resolución de versión para leases nuevas

- Para la pareja exacta `(variant_id, launch_profile_id)`, el daemon consulta primero `runtime_version_pin`. Si existe un pin, esa versión es la única candidata. No se cae al default ni a la versión de arranque si el pin falta del catálogo, pertenece a otra familia, dejó de ser `VALIDATED`, `DEFAULT` o `RETAINED`, no está instalada en el host adoptado, no coincide con la versión observada o perdió su compatibilidad.
- Si no existe pin, se usa `runtime.default_version_id`. Si el runtime no tiene versión predeterminada, la lease falla con `runtime_default_missing`. La configuración inicial del bridge, la versión más reciente y el orden del catálogo no sustituyen el default.
- La versión seleccionada debe pertenecer al runtime configurado y, en hosts adoptados, tener exactamente una instalación `EXTERNAL_ADOPTION`/`EXTERNAL` para el host. La versión textual observada por el host debe coincidir antes de publicar el catálogo o admitir la lease.
- Al crear la lease, LARM persiste el `runtime_version_id` elegido en `RuntimeLease.constraints`. Antes de activar una lease encolada vuelve a resolver la pareja y exige el mismo ID. Si el pin o el default cambió, la activación falla con conflicto y el cliente debe solicitar otra lease; no se altera una lease ya activa.
- Las referencias cualificadas de instancias y endpoints se separan por `(variant_id, runtime_version_id)`. Un cambio de pin no reutiliza ni reasigna referencias de otra versión.

## Campos y efectos de las operaciones P032

- `POST /api/v1/runtime-versions/{id}/update`: `{storage_location_id, strategy, profile_lock_hash, external_host_id}`. El ID de ruta identifica la versión candidata; runtime, versión y artefacto se resuelven del catálogo. La operación instala side-by-side y no modifica el default ni pins existentes.
- `POST /api/v1/runtime-versions/{id}/pin`: `{variant_id, launch_profile_id}`. El ID de ruta identifica la versión que se quiere fijar. La fila durable enlaza esa versión con la pareja exacta; si la pareja ya tenía pin, el mismo comando lo reemplaza tras superar lifecycle, instalación y compatibilidad. Devuelve un recibo idempotente.
- `DELETE /api/v1/runtime-pins/{variant_id}/{launch_profile_id}` retira el pin para leases futuras y no cambia las leases activas.
- `PATCH /api/v1/runtimes/{id}/retention-policy`: `{keep_last_validated}` con `If-Match`; el entero permitido está entre 2 y 50 y el valor inicial es 3. El cambio usa CAS e idempotencia.
- La retención protege el default, los pins, benchmarks, comparaciones, certificaciones, leases activas e instalaciones `ADOPTED`/`EXTERNAL`. Hasta que el worker de limpieza duradero esté conectado y verificado, no se realiza ningún borrado físico.

## Compatibilidad y oráculos

- Esta revisión no añade campos a `RuntimeUpdateRequest`, `RuntimePinRequest`, `RuntimeVersionPin`, `RuntimeRetentionPolicy` ni a `RuntimeLease`; concreta el orden y el comportamiento de resolución que exige 3.11.0.
- Un pin incompatible o no cualificado y un default ausente son errores visibles y no autorizan fallback.
- Cambiar o retirar un pin afecta sólo solicitudes nuevas; una lease conserva la versión persistida al crearla.
- Un reinicio o reintento idempotente conserva la pareja y la selección originales. La limpieza no elimina ninguna versión protegida ni una instalación externa.
