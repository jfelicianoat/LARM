GET /models y /models/{id} representan grupos CanonicalModel; GET /models/{id}/variants enumera variantes. Las acciones /models/{id}/move, verify, update, promote, delete-plan y DELETE /models/{id} reciben ModelVariant UUID (path_id_semantics en tabla). Para evitar ambigüedad el cliente usa variant_id explícito al construir acción y nunca transmite ID de grupo. DELETE exige If-Match y query approval_id+plan_hash de su delete-plan; no body implícito. El prompt de UI debe impedir mezclar IDs. Tauri usa transporte HTTP desde backend nativo con token bootstrap seguro; frontend no recibe secreto de admin ni habilita CORS wildcard para funcionar.

DTOs de escritura son distintos de registros: StorageLocationCreate sólo name/root/reserve/priority/autoplacement/class hint; GUID,canonical_path,capacity,free,state y timestamps los calcula el servidor. LaunchProfile hash lo calcula el servidor. Watch cursor/ETag/next_run no editables por CRUD. PATCH notification sólo read bool. Search q vacío significa omitir filtro de texto conservando otros filtros, no usar una cadena wildcard inventada.

Áreas adicionales incluidas en la tabla: runtime-installations/backends, external-hosts y source-accounts (lectura protegida; secretos nunca respuesta). Basic credential y OAuth callbacks usan schemas específicos. OAuth callback exige state/PKCE, no Bearer de un navegador externo; no es una vía de bypass para cualquier otra operación. Installation request usa InstallRequest y campos derivados de estado/ownership los fija el servidor.

Model detail se sirve en GET /variants/{id}/detail con VariantDetail; lectura de distribuciones/revisiones/bundles/artifacts/locations/provenance y StorageAnalysis tiene rutas explícitas en la tabla. GUI no accede SQLite ni calcula respuestas de servidor. Metadata de credenciales requiere credentials:read, separado de read del Broker, y nunca incluye secret. Cleanup requiere plan/approval/hash y guards, no acción automática del analyzer.

Las representaciones y reglas de los requisitos corregidos están completadas en [contrato 11](11_CONFORMIDAD_V3.md); aplicarlas junto con este contrato.

P052 3.1.0: el flujo de descarga es preview (`POST /download-plans`) → selección de destino → confirmación del operador → job (`POST /downloads`). El preview devuelve `DownloadPlanResponse`, no reserva ni crea jobs; la ejecución requiere `ExecuteDownloadPlan.operator_confirmed=true` y el hash exacto del plan.

P052 3.10.1: `DownloadPlanResponse.source_candidates` presenta cero a 16 mirrors cualificados y sus mapeos por fichero; `source_id` identifica la fuente principal de la variante y sigue disponible aunque la estimación sea ESTIMATED o UNKNOWN o no existan mirrors. El hash del plan liga la fuente principal, la lista de alternativas y sus mapeos, y el operador confirma tras revisarlos. Cada fallback transitorio emite `download.mirror.failed` desde outbox durable; la procedencia final conserva source_id y revision_key por artefacto.

P028: `POST /api/v1/adapters/import` es job202 con Idempotency-Key; la aceptación persiste `adapter.import` + replay por30d + `adapter.import.queued` en event/outbox en una transacción. El job expone sólo JobState sanitizado. Al publicar emite `adapter.imported`; un terminal fallido emite `adapter.import.failed`, ambos desde outbox con resource/correlation IDs. `POST /api/v1/adapters/export` devuelve201 CommandReceipt y su evento se confirma en la misma transacción de exportación. Un timeout/desconexión no abandona un commit aceptado.

P028 registro remoto: `GET /api/v1/adapters/registry` devuelve la configuración efectiva, el último RegistryCheckpoint y las revocaciones durables; `POST /api/v1/adapters/registry/sync` recibe `{}`, exige `Idempotency-Key` y `adapters:write`, consulta sólo la URL HTTPS configurada y responde200 con RegistrySyncReceipt. La aceptación del checkpoint, revocaciones nuevas y `adapter.registry.synced` se confirma en una transacción. Replay idéntico no genera evento ni mutación. La petición externa no reenvía Authorization, cookies ni credenciales, no sigue redirects y limita el índice a16MiB; el default TLS valida la cadena del certificado.

## Revisión 3.12.0 — primera adquisición

DownloadPlanResponse.acquisition es opcional para compatibilidad y obligatorio en planes remotos nuevos; se sella en preview_hash y plan_hash. Ingesta y snapshot publican eventos/outbox en una transacción, con replay sin duplicación. Reglas completas: [revisión 3.12.0](REVISION_3_12_0_P044_P052.md).

## Revisión 3.12.1 — binding del plan source

La firma source.download_plan recibe SourceDownloadPlanRequest con acquisition opcional; referencia pública, hash upstream y mapa de IDs centrales permiten seleccionar una revisión sin consultar IDs privados. Selección y copia exacta source_acquisition_v1 quedan selladas. La petición HTTP del usuario se conserva. [Reglas y oráculos](REVISION_3_12_1_SOURCE_ACQUISITION.md).

## Revisión 3.13.0 — reinicio explícito de transformaciones

Autorizada por el operador el2026-10-30. `POST /api/v1/transformations/{id}/restart` identifica el trabajo anterior, exige `jobs:write`, `Idempotency-Key` e `If-Match`, y reutiliza `ExecutePlan`/`JobReceipt` con respuesta202. Sólo FAILED/FAILED_RECOVERABLE sin output publicado; input original íntegro, plan nuevo confirmado, cualificación/espacio/guards/aprobación actuales, CAS y un único incremento de attempt. El replay liga actor, job, cuerpo y revisión y conserva el recibo original aunque el trabajo avance. Historial y temporales se conservan con ownership; COMPLETED/CANCELLED siguen terminales. La aceptación exige los oráculos H07 y proceso real, sin sustituirlos por esquemas o mocks. [Reglas y oráculos completos](REVISION_3_13_0_P093.md).
